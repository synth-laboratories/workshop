## 1. `typecheck` — the approval kind Track D needs does not exist in the renderer

```text
src/renderer/src/runtime/sessionView.ts(1439,4): error TS2322
  Type '"plugin_lifecycle"' is not assignable to
  '"shell_command" | "paid_compute" | "sidecar_lifecycle" | "credential_access" | "permission" | undefined'
```

Something already produces a `plugin_lifecycle` approval kind; the renderer's
union does not include it. This is exactly the seam Track D crosses — when a
human triggers a plugin lifecycle action, the approval that comes back is a kind
the renderer cannot type. Track D starts by widening this union, not on a clean
tree.

## 2. `test:rust` — the whole suite is dark

```text
error[E0432]: unresolved import `crate::domain`   --> tests/../src/storage/event_journal.rs:3
error[E0432]: unresolved import `crate::domain`   --> tests/../src/storage/models.rs:1
error[E0433]: cannot find `http` in `crate`       --> tests/../src/cloud/intern/client.rs:74
error[E0433]: cannot find `domain` in `crate`     --> tests/../src/cloud/intern/ingestion.rs:283,284,286
error[E0433]: cannot find `visuals` in `crate`    --> tests/../src/storage/live_spool.rs:96,121
error: could not compile `synth-desktop` (test "intern_protocol") due to 8 previous errors
```

Note the paths: `tests/../src/...`. The `intern_protocol` integration test
`#[path]`-includes library modules into a separate test crate, where
`crate::domain`, `crate::http`, and `crate::visuals` do not exist. It is a
structural break, not a transient error.

Because `cargo test` aborts on the first target that fails to build, **zero Rust
tests ran** — the output contains no `test result:` line at all. Every Rust
assertion in the repo is currently unenforced.

*Caution for the harness work:* `npm run test:rust` is `cargo test … | tail -40`
in a pipeline, so the shell reports the exit status of `tail`, not `cargo`. The
command "succeeds" while the suite fails. Any wrapper that checks this script's
exit code inherits the lie.

## 4. `test:a11y` — 3 failures, and two of them are real

All three failures are source-text assertions rather than behavioral tests.
They split into one drift and one genuine regression.

### Drift (1)

`v02_surface_invariants.test.mjs:40` — *"optimizer MCP recipe starts cannot
bypass the typed approval broker"*. Its last assertion expects
`desktopBridge.ts` to contain `event.source !== "codex" && !isApprovalBoundary`;
the source now reads `!event.kind.startsWith("approval.")`. The invariant holds
through a renamed implementation. The test is asserting a variable name that was
refactored away.

### Genuine regression (2)

`account_view.test.mjs:117` — *"the renderer never accepts API-key material"* —
and `a11y_surface.test.mjs:180` — *"Synth API settings keep routing in TOML while
credentials remain in native custody"*. Both fail on the same two facts in
`components/BackendSettings.tsx`:

```text
:107   apiKey: apiKey.trim()      passed to bridges.config.update()
:169   type="password"            "Synth API key" input, placeholder "sk_…"
```

A deliberate feature — paste your Synth API key in Settings to connect — now
does precisely what two standing invariants forbid: the renderer accepts key
material and forwards it. Neither test was retired, so they are correctly red.

The user-facing contradiction is worse than the red tests. `:257` still renders,
directly above the key form:

> "Routing is stored in TOML. Credentials must already exist in a private env
> file read only by the native host."

The screen claims native custody while offering a field that takes the
credential in the renderer.

**This is a product decision, not a test fix.** Either the invariant is
deliberately retired — in which case the copy at `:257` must change and both
tests must be rewritten to assert whatever custody rule now applies — or the
feature violates it and the feature changes. Do not make the assertions pass by
editing them to match the code; that converts a live finding into a green wall,
which is the failure mode the pre-qualification audit named.

Related: audit critical #1 concerns credential forwarding on the gateway path.
This is a different sink but the same custody question.

## Consequences for Track F

1. The Rust suite must compile before any Track C/D Rust test is worth writing.
   Fixing `intern_protocol`'s module inclusion is the first harness task.
2. `test:rust`'s `| tail -40` must go, or the harness cannot tell pass from fail.
3. The `plugin_lifecycle` union gap is on Track D's critical path and is already
   failing typecheck — fix it there, not as a drive-by.
4. Source-regex tests are the dominant shape in `tests/*.test.mjs`. They drift
   (case 1) and they cannot distinguish "renamed" from "removed." Track F's new
   assertions should be behavioral; existing ones should not be extended.
5. Nothing here can be attributed to v0.4 work. Re-run this baseline after each
   track lands and diff against it.
