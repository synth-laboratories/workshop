# Adapter distribution — Synth-published LoRAs for `2.1-ft`

Status: proposed 2026-08-21
Parent: [v0.7-lora-catalog.md](./v0.7-lora-catalog.md)

The catalog and the policy pin are built: the daemon serves selectable model
ids and the picker binds one per turn. What is missing is the supply. A user
can only choose `synth/Laguna-XS-2.1-ft` if Synth can publish an adapter and
they can install it.

Wasabi first, HuggingFace second, MinIO for the dev loop.

## What already exists, and what does not

- **Bytes**: `core/data/blob/` in the backend is a working S3 layer —
  `upload_file`, `download_to_file`, `get_presigned_url`, `S3Config` driven by
  `WASABI_*` and already contemplating a `minio` endpoint. Nothing new is
  needed to move bytes.
- **A client with no server**: `CloudOptimizerClient` calls
  `/api/v1/optimizers/checkpoints` for search, get, patch, archive, publish,
  and download. **Those routes do not exist.** `routes_optimizers.py` has a
  single `/runs/{run_id}/smr-optimizer-checkpoints`. The hosted half of the
  union catalog is a client written against an unimplemented API, so this
  lane is greenfield on the server and mostly wiring on the desktop.
- **Local identity**: `local_lora.rs` already digests an adapter tree and
  stores it at `state_root/loras/{hex}/`. Published adapters reuse that
  identity rather than inventing a second one.

## Locked shape

```text
training run ──emits──> mlx-lora.v1 tree
                             │
                        publisher CLI  (digest, manifest, upload)
                             │
              ┌──────────────┴──────────────┐
              ▼                             ▼
      Wasabi (authority, private)   HuggingFace (mirror, later)
      synth-artifacts/adapters/     synth/Laguna-XS-2.1-ft
              │                             │
              └──────────────┬──────────────┘
                             ▼
              backend  /api/v1/adapters
              authenticates the account, reads with its own credentials
                             │
                       streams bytes
                             ▼
                   Workshop download + verify
                             │
                  state_root/loras/{digest}/
                             ▼
              policy `synth/Laguna-XS-2.1-ft`
```

Rules:

- **The digest is the identity.** `sha256` over the adapter tree, computed the
  same way `local_lora::digest_directory` computes it. A publish that changes
  bytes is a new digest, never an in-place update of an old one.
- **The manifest travels with the bytes.** Everything a client needs to decide
  whether to install is in the manifest, not in a database the client might
  not reach.
- **Bytes are immutable; rows are mutable.** Names, notes, tags, and
  withdrawal live in the catalog. Never rewrite a published object.
- **Nothing is publicly readable.** No adapter object is world-readable and
  Workshop never reaches object storage directly. The backend authenticates
  the account and reads the bucket with its own credentials, so access is
  decided in one place and no bearer-capable URL is left in circulation.
  Adapters are single-digit megabytes, so streaming through the API costs
  little; a presigned redirect is an optimisation, not a requirement.
- **Wasabi is authority, HuggingFace is a mirror.** The mirror is published
  from the same manifest by a job, never hand-uploaded, so the two can be
  compared byte for byte.
- **One base pin per adapter.** An adapter names the exact base revision it
  was trained against and refuses to install onto anything else.

## The manifest

`manifest.json`, written by the publisher, uploaded beside the weights:

| Field | Meaning |
|---|---|
| `schema_version` | `synth-adapter.v1` |
| `digest` | `sha256:<hex>` over the tree; the catalog id |
| `base.model_id` | `poolside/Laguna-XS-2.1-NVFP4-mlx` |
| `base.revision` | the exact weights revision it was trained against |
| `lora.rank` / `lora.scale` | sampling-relevant shape |
| `lora.modules` | count and key list of adapted projections |
| `provenance` | run id, algorithm, dataset id, step, created_at |
| `metrics` | held-out scores, and the decode cost measured at p10 |
| `files[]` | `{path, bytes, sha256}` for every file in the tree |

`metrics.decode_tokens_per_second_p10` is measured with the matched-condition
protocol in `scripts/adapter_swap_spike.py`, on a quiet machine, and carries
its measurement floor. A cost number without its floor is not publishable.

## Storage layout

```text
s3://synth-adapters/
  laguna-xs-2.1/
    ft/
      sha256-<hex>/
        manifest.json
        adapter_config.json
        adapters.safetensors
```

Flat, digest-addressed, no `latest` alias in the bucket. Which digest is
current is a catalog decision, not a path convention — an alias in object
storage is how two clients end up disagreeing about what `latest` meant.

## Lifecycle

| Stage | Who | What happens |
|---|---|---|
| **Produce** | a training run | emits an `mlx-lora.v1` tree; already upserts a local catalog row from `checkpoint.created` |
| **Promote** | us | pick the candidate; nothing automatic — a run emitting a checkpoint is not a decision to ship it |
| **Publish** | publisher CLI | digest the tree, write the manifest, upload objects, `POST /adapters` to create the row |
| **Index** | backend | rows with entitlement, base pin, withdrawal state; the list the app reads |
| **Offer** | Workshop | show adapters whose `base.revision` matches the installed weights |
| **Download** | Workshop | presigned GET per file, verify each `sha256`, then verify the tree digest |
| **Install** | Workshop | land in `state_root/loras/{digest}/`, upsert the catalog row, register the policy |
| **Select** | user | picker binds `synth/Laguna-XS-2.1-ft` on the next turn |
| **Update** | us → user | a new digest is offered; the installed one keeps working until replaced |
| **Withdraw** | us | row marked withdrawn; new installs refused, existing installs flagged, never silently deleted |

## Compatibility gate

`is_laguna_compatible` currently tests whether the base-model string contains
`laguna` or `poolside`. That is enough while adapters are hand-imported and
wrong the moment we distribute them: an adapter trained against one Laguna
revision would apply silently to another.

Install refuses when `manifest.base.revision` differs from the installed
weights' revision, and the error names the revision required. Refusing beats
warning: a mismatched pair produces plausible tokens, so nothing downstream
will notice. The daemon keeps its own check at registration, so a
hand-registered path cannot bypass the rule.

## MinIO first

`docker-compose.yml` gains a MinIO service and a bucket-init step. The
backend's `S3Config` already takes `endpoint_url`, so MinIO and Wasabi differ
by configuration, not code — which is the point of doing MinIO first. The
publisher CLI and the download path are exercised end to end locally before
any production credential exists.

Credentials follow the rung scheme (`~/.synth/<rung>.env`); bucket names and
prefixes are code, not environment, so a misread variable cannot silently
publish to the wrong place.

## HuggingFace second

Same manifest, published as a repo revision by a mirror job that reads the
Wasabi objects. Two differences worth designing for now:

- **Anonymous reach.** HF needs no Synth account, which makes it the right
  channel for an openly published adapter and the wrong one for anything
  entitlement-gated.
- **Revisions, not digests.** HF addresses by commit sha. The manifest still
  carries our digest, and the client verifies it after download, so the
  identity does not change with the channel.

The app gains a second download source implementation behind the same verify
and install path. Source selection is per-row, from the catalog.

## Phases

- **P0 — manifest and publisher. Done.** `tools/adapters/synth_adapters.py`
  digests a tree, writes the manifest, uploads by digest, and pulls with
  verification. Proven against MinIO, including a tamper check: one flipped
  byte in a published object makes the pull refuse.
- **P1 — backend delivery. Done.** `/api/v1/adapters` lists
  manifests, serves one manifest, and streams one file, each behind API-key
  auth. The bucket is the source of truth, so there is no second index to fall
  out of step with the bytes. Required rather than optional: since nothing is
  public, this route is the only way a client obtains an adapter.
- **P2 — desktop install path. Done.** Status and download commands, per-file
  and tree verification, base-revision gate, install through the catalog's own
  import, policy registration, and a card in Settings → Models. Proven end to
  end against MinIO.
- **P3 — Wasabi. Publishing only.** The publisher writes into the existing
  private `synth-artifacts` bucket under `adapters/`, so no new bucket and no
  bucket policy are involved. Credentials reach the CLI through `railway run`,
  which injects the deployment's own variables into the process — they are
  never copied into a local file. Unverified until a publish runs.
- **P4 — HuggingFace mirror. Written, unverified.**
  `synth_adapters.py mirror` republishes from the object store rather than
  from a local tree, verifying each file before upload, so the channels cannot
  drift and a corrupted object cannot be laundered into a channel with no path
  back to the authority. Needs a repo and a token to run.

## Decisions

1. **Every plan can download it, and every download is authenticated.**
   `2.1-ft` is not entitlement-gated: any signed-in account may install it.
   That is not the same as public — nothing is world-readable, and the client
   goes to the backend, which reads object storage on its behalf.
2. **Shown, and downloaded on purpose.** Workshop surfaces the published
   adapter whether or not it is installed, with a Download action and progress
   — the same shape the base weights already use in Settings → Models. It is
   never installed without the user asking, and it is never hidden until they
   go looking for it.
3. **One finetune.** A single curated adapter served as
   `synth/Laguna-XS-2.1-ft`. The policy registry can hold several and the
   picker will render whatever it is given, but nothing in the product assumes
   a menu yet.
4. **A local CLI publishes.** Not a backend endpoint. Production credentials
   stay on the operator's machine, and publishing stays an act someone
   performs rather than a route that could be called.

## Not this

- A `latest` pointer in the bucket.
- Auto-installing an adapter a user did not choose.
- Publishing a cost number without the measurement floor it was taken with.
- Deleting a withdrawn adapter's bytes out from under an install that is
  working.
