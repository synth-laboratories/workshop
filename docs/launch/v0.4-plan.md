# v0.4 — Plugins IA + right-panel presentation: review and plan

> **Status 2026-08-15.** Tracks A–E4 are implemented on `v0.4-plugins`.
> Track F is partly done: the Rust suite was restored from non-compiling to
> green and the codex fixture waits were made load-tolerant, but the harness
> rebuild (real app launch, fake sidecar, un-stubbed install) and Playwright
> triage are **not** done. See §8 for what remains and why.

**Branch:** `josh/v04` (from `origin/dev` @ `4c32e75`)
**Worktree:** `~/Documents/GitHub/workshop-v04`
**Reviewed:** 2026-08-15
**Scope:** two incoming proposals — the Plugins sidebar section, and Trace V5
inspection + product-wide right-panel presentation.

Both proposals were written against `workshop-v03-plugin-mcp`
(`josh/v03-optimizer-plugin-mcp-e2e`), which is **behind** `dev`. `dev` is the
superset. Several premises in both no longer hold, and one of them makes a whole
part of the second proposal unnecessary.

The unifying goal is right: today a capability's *destination*, its *lifecycle
status*, and its *presentation* are three unrelated mechanisms that the human and
the agent reach by different paths. v0.4 makes each one thing.

| Concern | Today | v0.4 |
|---|---|---|
| Where a capability lives | two ad-hoc sidebar sections | one `Plugins` section over `PluginNavEntry[]` |
| Whether it is usable | a local boolean + a duplicated 13-phase map | `pluginPresentation(PluginStatus)` |
| How a record is shown | `DataPage` inlines visual lifecycle; MCP has its own path | one `PresentationService`, both callers |
| Who may act on it | agent can install/remove; human cannot | same commands, both surfaces |

### 1.3 The plugin lifecycle engine already exists — and only agents can reach it

This corrects my earlier reading of this branch. `PluginService::manage` /
`mutate` / `execute` (`src-tauri/src/plugins/service.rs:128-300`) is a complete
lifecycle engine: approval-broker authorization, active-run guards, retention
classes, `PluginActionReceipt` recording, and dispatch into
`OptimizerSidecarManager` (`install:414`, `start:486`, `stop:724`,
`uninstall:730`). It is `pub(crate)`, reachable only over loopback
`/v1/plugins/*` (`visuals_ipc.rs:1897-1913`).

`synth_plugins_mcp.rs:82` already advertises to agents:

```text
list · status · capabilities · enable · disable · install · start · stop · update · remove
```

The renderer's entire surface is three read-only commands (`lib.rs:993-1025`).

> **An agent can install, update, disable, and remove the Optimizers plugin
> today. The human cannot, from anywhere in the UI.**

The first proposal's acceptance criterion #6 — "no lifecycle control until the
command exists" — is satisfied on the agent path and inverted on the human path.
Phase 3 is therefore *cheap*: wrap the existing `manage` in Tauri commands, not
build an engine. It should land in v0.4 (D3).

Two behaviors to get right when exposing it:

- `disable` only flips the registry flag (`service.rs:249-252`); the sidecar
  keeps running, and unlike `stop`/`remove` it has **no active-run guard**. So
  `enabled: false` with `service.activeRuns: 3` is representable. A row reading
  only `Disabled` would imply the paid runs stopped. Presentation must show the
  active count in that state.
- `plugins_status` ignores its `plugin_id` (`lib.rs:997` is literally
  `let _ = plugin_id;`), so `status("visuals")` returns optimizers' phase.
  `plugins_list` returns a one-element vector. Validate the id;
  `plugins_set_release_channel:1011` already shows the pattern.

### 1.4 The proposed binding enum would reject existing visuals

`visuals/models.rs:296-304` allows:

```text
inline | trace_v5 | local_cas | run_ref | live_sse | fixture | optimizer_run
```

The proposal's enum lists five kinds and omits `inline`, `run_ref`, and
`optimizer_run`. **Add `query_snapshot` to the existing list; do not replace it.**

### 1.5 The trace query foundation already exists

`trace_index` (`storage/migrations.rs:367-395`) already carries nearly every
field the proposed `TraceQuery` filters on — `model`, `provider`, `harness`,
`benchmark`, `task_id`, `lifecycle_status`, `capture_status`, `reward`,
`cost_usd`, token counts, `span_count`, `event_count`, `tool_call_count`,
`error_count`, `started_at`, `ended_at`, `duration_ms`, `has_media`,
`has_evidence`, `search_text` — with indices on `model`, `(benchmark, task_id)`,
and `reward`. Track C is a query compiler over an existing table.

Gaps to close in the AST or the schema, not to assume away: `container_id`,
`session_id`, and `run_id` are not columns; there is no `created_at` (map
`created` / `order_by: created_at` onto `started_at`); `digest` is the primary
key, not a filterable column alongside `trace_ids`.

## 2. The abstractions

Three, each owning one of the three concerns above.

```ts
// runtime/pluginNav.ts — the sidebar's contents, one entry per destination
export type PluginNavEntry = {
  id: "visuals" | "reports" | "optimizers" | "inventory";
  label: string;
  testId: string;                     // open-visuals | open-reports | ...
  view: ViewState["kind"];
  kind: "builtin" | "managed";
  pluginId?: string;                  // managed only
};

// runtime/pluginPresentation.ts — the one owner of the 13-phase map
export type PluginPresentation = {
  label: string | null;               // "Ready" | "Disabled" | "Error" | null
  tone: "neutral" | "success" | "warning" | "danger";
  isUsable: boolean;
  isTransitional: boolean;
  activeRuns: number;                 // surfaced even when disabled (§1.3)
  a11yLabel: string | null;           // never color-only
};
```

Built-ins are **not** registry rows. The registry knows only `optimizers`, and
`plugins_list` is single-element by construction; a Plugins section sourced from
the registry would render one row.

```text
PresentationService (native)
  ensure_trace_inspector(trace_id)      → digest-bound vis_trace_<digest>
  ensure_optimizer_run_visual(run_id)
  ensure_query_catalog(snapshot_id, template_id)
  show(visual_id)
```

`DataPage.inspectTrace` and every MCP facade call this. Today that lifecycle
logic lives in a React component, which is why the agent path has no equivalent
and would drift the moment one is written.

```text
useAppController
  └─ pluginStatuses  +  refreshPluginStatuses()
      ├─ Sidebar        (reads)
      └─ OptimizersPage (receives; owns no poller)
```

### Track D — human lifecycle parity

- Renderer bridge methods; a plugin detail panel on the Optimizers page with

- Show `activeRuns` in the `disabled` state (§1.3), so "Disabled" never implies

- No lifecycle control in the sidebar. The row carries status and navigation;

### Track E — right-panel presentation (agent path)

**E1 — `PresentationService`.** Lift `inspectTrace` out of `DataPage` into a
native service owning deterministic ids, binding validation, digest-bound reuse,
template selection, provenance, and the show event. `DataPage` and MCP both call
it. Without this, E2 forks the logic on day one.

**E2 — `synth_traces` MCP.** `trace_manage({ operation: "get" | "open" | ... })`;
`open` resolves a trace, validates inspectability with the same policy as
`traceInspectability`, and calls `ensure_trace_inspector` + `show`. Returns
trace id, digest, visual id, and inspectability. Refuses to bind one trace's
inspector to another digest.

**E3 — typed query + snapshots.** `TraceQuery` AST compiling to parameterized
SQL over `trace_index` (§1.5), read-only, hard result cap, bounded text search,
no JSON-path predicates in v1. Snapshots are immutable: query AST + schema
version + result ids + facets + `queried_at` + result digest. A refresh mints a
new snapshot; it never mutates an existing presentation.

**E4 — `query_snapshot` binding + catalog templates.** Add the kind to the
existing allowlist (§1.4); add `trace.catalog.v1` under
`visuals/families/analysis/`; rows drill into the digest-bound inspector; the
zero state states the filter and the retrieval time.

**E5 — generalize.** `optimizer.run_catalog.v1`, `container.catalog.v1`,
`usage.breakdown.v1`, `plugin.catalog.v1`, plus a `container_manage` facade to
match the other domains (§1.6). Templates are curated and trusted — agents choose
domain, filter, record, and presentation; they do not author the renderer for
operational data.

**Three costs the proposal does not price.**

*New templates are not just files.* `visuals_ipc.rs:26-46` gates every template
on six base authoring checks — `rendered`, `noOverflow`, `primarySurfaceVisible`,
`temporalControls`, `traceInspector`, `realEvidence` — plus `screenshotInspected`,
and more by family. Each of the five catalog templates in E4/E5 has to earn that
evidence.

*Query snapshots need a home.* The trace tables are `trace_imports`,
`trace_bundles`, `trace_bundle_members`, `trace_assets`, `trace_index`,
`trace_tags`, `trace_projection_cache`, `trace_annotations`
(`storage/migrations.rs:1142`). There is no snapshot store. E3 needs a new table
and migration holding snapshot id, domain, query schema version, normalized AST,
result ids, facets, `queried_at`, and result digest — immutable after insert.

*A new MCP server is a packaging change.* `session/codex/home.rs:414-419` writes
`[mcp_servers.<name>]` into Codex's `config.toml` for five bundled binaries that
must exist beside the executable. `synth_traces` needs a Cargo bin target, an
entry in that list, and inclusion in the packaged bundle — not just a new
`.rs` file.

**And one inconsistency to settle first.** That same loop skips the
`synth_optimizers` MCP server entirely when the plugin is disabled
(`home.rs:423-425`) — the identical "capability vanishes when disabled" failure
the sidebar change exists to fix, on the agent surface instead of the human one.
After Track B the sidebar will show `Optimizers · Disabled` and stay navigable
while the agent silently loses the tool and cannot report why. Either the server
registers and its operations return a typed `plugin_not_ready`, or the
divergence is deliberate and documented. Recommend the former; it is the same
principle as criterion #3.

**Invariants** (unchanged from the proposal, and correct): no raw SQL through
MCP; no writes in a query facade; no unbounded lists; no direct database paths;
sealed archives immutable, projections regenerable, annotations a separate
overlay; opening a presentation never pins, exports, publishes, or mutates.

### Track F — a harness that can fail (prerequisite, D-decided)

The audit's test-integrity finding is that Playwright never launches the app —
it stubs `window.synthRuntime` over Vite — that Bombadil's `subagentsValid` is a
tautology, that the overlap test measures its own `waitForTimeout`, and that real
plugin install is stubbed by `cfg!(test)`. Three suites encode current bugs as
expected behavior. Tests written in those shapes for Tracks A–E would go green
and prove nothing.

v0.4 fixes the harness **for the surfaces it touches**, not the whole estate
(that is the testing repo's reform train):

- Real app launch for the sidebar and plugin-status paths, so `plugins-nav`,
  the four destinations, and the disabled/error rows are asserted against the
  running renderer rather than a stub.
- A fake optimizer sidecar the plugin tests drive through `ready`, `disabled`,
  `not_installed`, `degraded`, and `error` — including `enabled: false` with
  `activeRuns > 0` (§1.3), which no current test can produce.
- Un-stub plugin lifecycle for Track D: `cfg!(test)` must not be what makes
  install succeed, or the parity work ships untested by construction.
- Baseline first: record which suites are red at `4c32e75` before Track A lands.
- Standing rule for this branch: every new assertion is shown failing against
  broken code before it lands.

## 6. Acceptance criteria

1. Exactly one sidebar section, `Plugins`, with Visuals / Reports / Optimizers /
   Data.
2. Routes, page state, and all four `open-*` test ids unchanged.
3. Optimizers never disappears when disabled, stopped, uninstalled, or
   unhealthy — and `optimizer-plugin-mcp.spec.ts` asserts that, inverted.
4. Sidebar status derives from `plugins.list()` through `pluginPresentation`,
   never a local boolean.
5. Exactly one component subscribes for plugin status, and no code path probes
   the sidecar on a timer while a page is merely open.
6. Every lifecycle action available to an agent is available to the human, under
   the same approval, active-run, and receipt rules — or is available to
   neither.
7. A trace inspector visual is reused only when its binding source equals the
   exact sealed digest.
8. Native UI and MCP reach the right panel through one `PresentationService`;
   neither owns visual lifecycle logic of its own.
9. Agents receive no raw SQL, no write operation in a query facade, and no
   database path.
10. Adding a second managed plugin, or a sixth presentable domain, is one more
    entry — not another redesign.

## 7. Risks

- **Green-wall risk.** The pre-qualification audit found that Playwright never
  launches the app (stubbed `window.synthRuntime` over Vite) and that several
  suites cannot fail. Tests written in those shapes for Tracks B–E would pass
  without proving anything. Every new assertion here must be able to fail —
  verify by breaking the code under test first.
- **Concurrent worktrees.** Eight other workshop worktrees are checked out; two
  touch `Sidebar.tsx` lineage. Rebase on `origin/dev` before landing.
- **`plugins_list` is single-element by construction.** Any UI that assumes it
  enumerates capabilities renders an empty Plugins section. Built-ins come from
  `pluginNav.ts`.
- **Test-id sweep.** `evalApi.ts`, `UsageSheet.tsx`, and `AccountPage.tsx` carry
  their own `*-open-inventory` ids. Distinct strings; a blind rename breaks them.
- **Approval deadlock precedent.** The audit root-caused GEPA `plugin_not_ready`
  to a circular approval wait with no timeout. Track D routes human actions
  through that same broker — exercise the reject and timeout paths, not just the
  approve path.
