## End-to-end tests (the v0.3 bar)

These are the product proofs. A theme is not done because a template exists; it is done when Workshop can run it live, the agent can keep updating the visual, the user can label, and VisualsBench can score the visual independently of the task score.

### E1 · VisualsBench (`evals/` — new family)

Think hard, in writing, about what a **good dynamically created visual** is, then encode that as VisualsBench. Do not reuse `evals/reference/old/visualbench` report packs as the contract; those are sealed Craftax GIF/HTML corpora. The new family lives under `evals/` (working name `visualsbench`) and grades agent-authored / live-updated Workshop visuals.

A good visual, for this cut:

- is bound **before** mutation and stays the same instance as evidence arrives;
- shows missing as missing (never coerces reward/attack/score to 0);
- is scrubbable, comparable across arms, and labelled without mutating a sealed Trace V5;
- makes the claim inspectable (zombie/skeleton attacks, party coordination, Harbor DEO delta) without reading the transcript;
- can be revised live by the agent after a user click/label.

VisualsBench scores those properties (legibility, honesty, update-in-place, label round-trip, compare-across-arms). Task metrics stay on the Craftax / DungeonGrid / Harbor graders. Both must pass.

### E2 · Craftax alignment — zombie and skeleton attacks

Three arms, same seeds, same visual family, attack evidence from engine NEV / combat payloads (not guessed from ASCII):

| Arm | Policy | What the visual must show |
| --- | --- | --- |
| **Baseline** | Unaligned Craftax policy | Zombie and skeleton *attacks* (player→mob and mob→player) as first-class series, not a footnote |
| **After alignment training** | Aligned policy (VeganCraftax / REB-009 shape: progress without directly harming zombies or skeletons) | Attack counts drop on the protected classes; progress/survival still visible; missing combat stays null |
| **After alignment + RLVR** | Same alignment objective, then RLVR | Whether RLVR preserves the refusal, recovers progress, or reintroduces attacks — the visual is the comparison, not a blog paragraph |

Pass when: one Workshop session can open the three arms side by side (or flip with shared cursor), label a zombie/skeleton incident, and the next turn sees that label. VisualsBench grades the visual; Craftax grades the policy.

Pass when: child roles/actions are legible in the visual *and* the subagent chrome; parallel children actually overlap in wall-clock (not a serialized “multi-agent” story); the parent transcript is not a dump of child chat; VisualsBench can score the live visual without the GameBench HTML report.

### E5 · ResearchAssistantBench → hosted Nemotron 3.5 Lightning SFT + CISPO → Shoal (last try)

The last thing v0.3 *tries*. E1–E4 can ship without it. This is the collaboration-specialist model: a Nemotron that writes clearly, models the user, sleuths data and systems, and makes live visuals — not an Intern that you leave running overnight.

**Student:** `nvidia/NVIDIA-Nemotron-3.5-Lightning-30B-A3B-BF16` (same Tinker catalog pin as Banking77 / Craftax hosted SFT). Do not silently swap Nano or a 256K peft id.

**Optimizers for these capabilities:** hosted **SFT**, then hosted **CISPO** (`loss_fn = "cispo"` on the owned Tinker / optimizers-beta path — the same CISPO used in GSM8K/Banking77 RLVR golds, named here because it is the algorithm, not a generic “RLVR family”). Do not swap in PPO/GRPO/DPO for this student without a new note.

**Dataset / bench:** **ResearchAssistantBench** in `evals/`, packaged as Harbor instances. Harbor owns task / workspace / verifier. Workshop is where a practitioner watches it. Visuals is **one split**, not the whole bench; VisualsBench (E1) is the grader for that split.

**Authoring — real sessions first, Harbor second, one by one.** Most tasks are not synthetic. Do a real interactive collaboration in the app (steer, labels, live visual, containers/optimizers as they actually happened), seal the session (transcript, visuals, traces, resource-refs), then turn *that* session into one Harbor instance. Add tasks as they accumulate; do not bulk-generate a fake corpus.

```text
Workshop session (chat + visual + labels + tools)
        ↓ seal
receipt: session id, visual ids, Trace V5 / optimizer / container refs
        ↓ one Harbor task
evals/.../researchassistantbench/<split>/<task-id>/
        workspace snapshot + verifier + provenance → session receipt
```

E1–E4 dogfood sessions are fair sources. A task without a session receipt is the exception and must say so.

| Split | Trains / grades | Harbor task shape |
| --- | --- | --- |
| **Writing** | Clear, specific, non-theatrical prose a practitioner can use | From a real session: write the result so a human can act |
| **Theory of mind** | Communicate *to this user*: what they already know, what would surprise them, what to show vs bury | Same session evidence, audience-fit grader — not just factual coverage |
| **Data sleuth** | Find patterns, findings, issues, bugs in datasets / traces / metrics | Seeded from the session’s actual anomalies; missing≠0; no invented correlations |
| **Systems sleuth** | Same instinct on **optimizers, containers, relays, sidecars** — and *visualize* them | Real GEPA/SFT/Craftax/Harbor journals from the session; finding cites a resource-ref |
| **Visuals** | Dynamic, open-ended, helpful visuals and summaries | E1 VisualsBench on the visual the session actually produced / should have produced |

Pipeline — **sessions → Harbor one-by-one → eval → SFT → CISPO**. Do not SFT from ungraded generations. Do not wait for a “complete” dataset before the first Harbor task exists.

```text
1. Collaborate for real in Workshop. Seal the session.
2. Convert that session into one Harbor ResearchAssistantBench task
     (train / val / held-out chosen at conversion; visuals split if the
     session’s claim is the visual). Provenance required.
3. Repeat. Baseline-eval any frozen held-out slice on
     base Nemotron Lightning, Luna, Terra, Laguna (pin SHAs).
4. Hosted SFT from graded train+val trajectories.
5. Hosted CISPO with Harbor verifiers + VisualsBench as reward.
6. Promote a digest-pinned checkpoint. Serve on Modal B200 behind Shoal.
7. Workshop can select the Shoal-hosted student as a collaboration target.
     Nemotron is not a composer target today; this cut is what makes it one.
```

**Shoal / Modal:** Shoal is the chat-completions gateway (`shoal-staging-dev` / `shoal-prod-production` on Railway) in front of hosted vLLM. It is never loopback. Serve the finetune on **Modal B200** (30B-A3B MoE needs that class; do not hide a smaller GPU behind the same model id). Pin: weights digest × vLLM image × Shoal model id × Modal app revision. Fail closed if the gateway would answer from a different checkpoint.

Pass when:

1. At least a held-out slice of ResearchAssistantBench exists, each task pointing at a real Workshop session receipt (or an explicit synthetic exception), and baseline scores exist **before** Lightning SFT.
2. Hosted SFT and CISPO runs are visible in Workshop (SFT live visual + CISPO/RL training visual), visual-first, missing≠0, child evals are resource-refs.
3. Held-out RAB (including the visuals split) improves vs base Lightning without collapsing writing/ToM into template spam.
4. Shoal chat completions for the pinned id hit the B200 deployment; a Workshop turn can open a live visual the student then updates.
5. The model is usable as a **collaboration** target (steer, label, interrupt). It is not Intern, not a background mailbox, and not a v0.3 launch blocker if the train/serve loop slips.

Do not: bulk-author Harbor tasks without a session; train on held-out; serve an unpinned “latest”; put this student on Intern chrome; call this a generic RLVR product; substitute PPO for CISPO quietly.

## Design criteria (v0.3)

Workshop is judged as a **collaboration agent**, not a SWE-bench substitute.

| Criterion | What it means here |
| --- | --- |
| Latency over max accuracy | Fast local Laguna and steerability beat “come back in an hour.” **Parallel subagents** are a speed investment when the work splits: spawn children, keep the parent in flow, show progress on the rail *and* on a live visual so parallelization does not become a black box. |
| Process legibility | The user sees what the agent sees (context) and what it is making (live visuals, child agents). |
| Shared workspace | Visuals, traces, diagrams, and labels are the work, not a report after the work. |
| Continuous steering | Click a point, label a span, edit a skill, toggle an MCP group, interrupt a child — without a new spec. |
| User agency | Context is inspectable and editable. The agent does not own a hidden prompt pile. |
| Skill, not substitution | Labelling, reviewing, and composing with the agent should sharpen the practitioner. |

Failure modes to design against: interruption fatigue, the human as bottleneck, black-box context, visuals that only update after the run is dead.

Out of this cut’s *product* claims: autonomous task completion, inbox/queue/PR-review as the primary interface, per-outcome pricing. Those are Intern.

### 2. Context — what the agent sees, as a Settings surface

Today context is scattered and mostly invisible:

- Workspace `AGENTS.md` is discovered from the conversation working directory (Codex order). There is no Workshop-owned instructions pane.
- Bundled skills (`use-synth-containers`, `use-synth-visuals`, `use-synth-optimizers`, `run-live-container-evals`, `author-synth-diagrams`) are `include_str!` copies installed into each Codex home. `skills_list` is name+description only. Slash menu can pick them. No toggle, no editor.
- **Workshop does not clone cookbooks.** `synth-cookbooks-public` is a sibling checkout. Named instances **rsync** one Banking77 GEPA recipe via `desktop-instance.sh` (`SYNTH_BANKING77_GEPA_COOKBOOK_ROOT`). The installed app never `git clone`s that repo. Cookbook `skills/` is currently a README; GEPA/containers skills live in those product repos. Visuals still ship from `workshop/visuals/`, “not cookbooks yet.”
- MCP lives on Connectors as a catalog (Bundled / Productivity / Development) with no group on/off that actually changes `enabled_tools`.
- Subagent compatibility already exists under **Settings → Models** (`model_multi_agent_*`, V1/V2/none). Keep it; move it into the Context section rather than inventing a second control.

**Cookbooks — opt-in clone, then a skill.** Default off. The Context viewer has an explicit control: clone `synth-cookbooks-public` (pinned tag/SHA, sparse: `skills/` + selected `cookbooks/` recipes, never the `gepa/runs/` residue) into `~/.synth-desktop/cookbooks/<pin>/`, **and include it in agent context**. Including it installs a bundled skill (working name `use-synth-cookbooks`) so the agent knows the checkout exists, what it may read, and that it must not treat run artifacts or private overlays as public recipes. Clone without the skill (or skill without a successful pin) is a broken state — the toggle is one action: clone → pin ready → skill on.

- Friends: public repo only. Private cookbooks stay a developer overlay, never this toggle.
- Same bar as Laguna download: progress, digest, cancel, Update. Off-network: last good pin still works; missing cookbook ≠ invent a recipe.
- Uncheck: stop advertising the skill and stop listing the checkout as writable/readable context. Do not delete the pin until Uninstall (Laguna analog).
- Context shows pin, last fetch, and whether a skill is **bundled** / **cookbook** / **yours**.

Add **Settings → Context**:

| Block | Shows | User can |
| --- | --- | --- |
| **Workshop `AGENTS.md`** | The instructions Workshop itself injects (bundled, versioned, read-mostly) | Read what the agent is told; copy. Edits to the bundled file are a product change, not a per-user override. |
| **Your `AGENTS.md`** | The workspace (or user overlay) file Codex already discovers | Open/edit in place; see whether it is present, empty, or overriding. |
| **Cookbooks** | Off, or public pin (tag/SHA, digest, path) | **Clone and include in context** (one toggle). Update pin. Uninstall. Off = no skill, no cookbook root in the session. |
| **Skills** | Bundled + `use-synth-cookbooks` (on only if cookbooks pin is ready) + user skills | **Edit** user copies; **toggle** include/exclude for new sessions. Off means not copied into the Codex home / not advertised. Cookbook-provided skills follow the pin. |
| **MCP groups** | Same groupings as Connectors (Bundled, Productivity, Development, plus any user servers) | Group on/off. Off must change what the session advertises, not just hide a card. |
| **Subagents** | Existing multi-agent compatibility presets/overrides | Same V1/V2/none controls, now next to the rest of context. |

Pass when: a practitioner can answer “what will this agent see on the next turn?” from Settings without opening `~/.synth-desktop` or a Codex home. Toggles and edits are the steering surface; they are not a hidden prompt dump. Cookbooks-off sessions never mention the checkout; cookbooks-on sessions have a ready pin **and** `use-synth-cookbooks`.

Do not: auto-clone on first launch; clone the full monorepo including `runs/`; auto-assemble a giant mystery system prompt; let chat rewrite Workshop’s bundled `AGENTS.md` without a product revision; toggle MCP by guessing tool names the schema does not list.

### 3. Dynamic visuals as the collaboration medium

The shared workspace is the visual, not the transcript.

v0.2 already streams into bound templates (`visual_stream_live_eval`, Craftax/Harbor/GEPA/SFT live shells, `analysis.visual.v1`, `blank.canvas.v1`, `annotation.overlay.v1`). That path is create → bind → maybe stream → look. v0.3 makes it a **back-and-forth**:

1. **Agent updates live.** The same instance mutates as evidence arrives *and* as the agent revises the spec (analysis blocks, canvas document, diagram source, overlay markers). Steering (`turn/steer`) and visual MCP are the same conversation, not a second product.
2. **User clicks to label.** Click a frame, span, candidate, trial, or chart mark → durable annotation (`note` / `bug` / `highlight` / `reward` / `acceptance` and labelling payloads) that the agent can read on the next turn. Overlay never mutates a sealed Trace V5 digest.
3. **Subagents stay first-class, not another visual pane — also a speed path.** Transport is done. Remaining: rail summary, dedicated Subagents workspace, child-thread detail ([`SUBAGENTS_UX_PROPOSAL_2026-08-12.md`](../SUBAGENTS_UX_PROPOSAL_2026-08-12.md)). Invest in **spawn/wait logic and the visuals that show parallel work**, not only chrome: when a task splits (DungeonGrid roles, Harbor DEO lanes, sleuth-vs-write), children run together so wall-clock stays in flow. Child process is legible on the rail *and* on the live visual; raw child chat does not flood the parent. Parallelization that the user cannot see is just another black box.

Pass when: a session can open a live visual, the agent can keep writing into it, the user can mark a point, and the next turn sees that mark — without exporting a CSV or starting a new run.

Templates that must get this loop, not only exist:

- Live families: Craftax (alignment attack series), Harbor DEO, DungeonGrid multi-agent, dig.bench, GEPA, SFT, GELO/GoEx (prompt-only floor proven; iterate), then OHCO
- Agent-authored: `analysis.visual.v1`, `blank.canvas.v1`, Mermaid/systems
- Evidence: generic Trace V5 + `annotation.overlay.v1`

VisualsBench fails a visual that only updates after the run is dead, that hides zombie/skeleton combat, or that cannot be labelled.
