# v0.4 — Plugins sidebar: review and implementation plan

**Branch:** `josh/v04` (from `origin/dev` @ `4c32e75`)
**Worktree:** `~/Documents/GitHub/workshop-v04`
**Reviewed:** 2026-08-15

This plan revises the incoming proposal against what is actually on `dev`. The
proposal was written against `workshop-v03-plugin-mcp`
(`josh/v03-optimizer-plugin-mcp-e2e`), which is **behind** `dev` — `dev` is the
superset, and three of the proposal's premises no longer hold.

The goal is unchanged and correct: collapse `Research` + `Data` into one
`Plugins` section, and give the sidebar and the pages **one abstraction** —
a list of plugin nav entries with a lifecycle status — instead of a hidden
boolean, a duplicated phase map, and a poll loop per component.

---

## 1. What the proposal got wrong about `dev`

### 1.1 There are four destinations, not three — `Reports` is missing

`Sidebar.tsx:484-512` renders **Visuals, Reports, Optimizers** under `Research`,
plus `Containers · Traces · Usage` under `Data`. The `reports` route
(`routes.tsx:41`, `routes.tsx:255`) and the `open-reports` test id landed on
`dev` after the proposal's worktree was cut.

Collapsing only Visuals/Optimizers/Data would leave `Reports` in a section with
no other members — the exact orphan the change is meant to remove.

**Decision needed (D1).** Recommended: four rows.

```text
Plugins  ⌄
  Visuals
  Reports
  Optimizers        Ready
  Data
```

### 1.2 Phase 3 is not "expose commands that already exist"

The proposal says the Rust service "has lifecycle capability internally —
install, start, stop, update, remove, enable/disable". `PluginService`
(`src-tauri/src/plugins/service.rs`) exposes only `new`, `open_default`,
`registry`, `status`, `capabilities`. `PluginRegistry` adds `set_enabled`,
`set_release_channel`, `record_receipt`, `receipt`.

The real lifecycle lives one layer down on the **optimizer sidecar manager**
(`src-tauri/src/optimizers/manager.rs`): `install:414`, `start:486`,
`ensure_ready:578`, `stop:724`, `uninstall:730`, `select_version:397`.
`PluginService::status` is a *projection* of that manager's sidecar status
(`service.rs:51-66`).

So phase 3 is real work: plugin-level commands must compose manager lifecycle +
registry `set_enabled` + `record_receipt` + policy, and decide what a plugin
action means for a plugin whose runtime is a sidecar. It is not a thin
re-export. Scope it as such or defer it.

### 1.3 An existing test asserts the opposite of acceptance criterion #4

`tests/playwright/optimizer-plugin-mcp.spec.ts:65-86` — *"disabled Optimizers
plugin removes navigation"* — stubs `enabled: false` and asserts
`expect(page.getByTestId("open-optimizers")).toHaveCount(0)`.

Acceptance criterion #4 says Optimizers must never disappear. This test must be
**inverted and renamed**, not merely adjusted. It is the one deliberate
behavior change in phase 1, and it is the only test that fails on structure.

## 2. What the proposal got right, confirmed against `dev`

- `bridges.plugins` exists and is wired (`desktopBridge.ts:789`); the command
  surface is exactly `plugins_status` / `plugins_list` /
  `plugins_set_release_channel` (`lib.rs:993-1025`,

- `PluginStatus` (`src-tauri/src/plugins/types.rs:40-66`) carries everything the
  sidebar, a detail panel, and a receipts view need.
- The phase→label map is already written once in `OptimizersPage.tsx:192-208`
  and covers all 13 phases in `types.rs:14-28`. Hoisting it is a pure move.
- Section open/closed state is local `useState` only (`Sidebar.tsx:182-184`);

- `research-nav` and `inventory-nav` appear **only** in `Sidebar.tsx` (483, 532).
  Retiring them is free. Every test binds to `open-*` destination ids.

## 3. Two findings that change the phase-2 design

### 3.1 `optimizer:status` is emitted and nobody listens

`lib.rs:2923-2932` subscribes to the sidecar manager broadcast and emits
`EventChannel::OPTIMIZER_STATUS`. The channel is declared renderer-side
(`protocolConstants.ts:24`) — and has **zero subscribers**. `LAGUNA_STATUS` at
`desktopBridge.ts:239` shows the exact `listen(...)` pattern to copy.

That dangling contract is why `OptimizersPage.tsx:166-168` polls
`plugins.status("optimizers")` on a **750 ms `setInterval`, unconditionally,
for the whole time the page is mounted**. Each poll runs
`manager().refresh()` — a live sidecar probe (`service.rs:52`).

Adding a second poller in the sidebar, as the proposal contemplates, doubles
that probe rate and puts it on every screen in the app. Phase 2 should
**subscribe to `optimizer:status` and delete the interval**, keeping a bounded
poll only as a fallback while a phase is transitional.

### 3.2 `plugins_status` ignores its `plugin_id`

`lib.rs:995-1001` is literally `let _ = plugin_id;` — every id returns the
optimizers status. `plugins_list` (`lib.rs:1005`) returns a one-element vector.

Consequence: `bridges.plugins.status("visuals")` would return
optimizers' phase and the UI would believe it. The sidebar must therefore
resolve managed status via `list()` + `pluginId` match (as the proposal says),
and phase 2 should add the missing validation to `plugins_status` so the lie
becomes an error.

## 4. The abstraction

One list, built in one place, consumed everywhere. Built-ins are **not**
registry rows — the registry only knows `optimizers`, and inventing fake
entries for Visuals/Reports/Data would be the inaccuracy the proposal warns
against.

```ts
// runtime/pluginNav.ts
export type PluginNavEntry = {
  id: "visuals" | "reports" | "optimizers" | "inventory";
  label: string;                      // sidebar destination name
  testId: string;                     // open-visuals | open-reports | ...
  view: ViewState["kind"];
  kind: "builtin" | "managed";
  pluginId?: string;                  // managed only
};

// runtime/pluginPresentation.ts
export type PluginPresentation = {
  label: string | null;               // "Ready" | "Disabled" | "Error" | null
  tone: "neutral" | "success" | "warning" | "danger";
  isUsable: boolean;                  // recipe launch allowed
  isTransitional: boolean;            // spinner
  a11yLabel: string | null;           // never color-only
};

export function pluginPresentation(status?: PluginStatus | null): PluginPresentation;
```

`pluginPresentation` is the single owner of the 13-phase map, moved out of
`OptimizersPage.tsx:192-208`. Consumers: `Sidebar`, `OptimizersPage`, future
plugin detail panel, recovery dialogs.

Ownership of the data:

```text
useAppController
  └─ pluginStatuses: PluginStatus[]  +  refreshPluginStatuses()
      ├─ Sidebar        (reads; renders status text per entry)
      └─ OptimizersPage (receives status + refresh; no own poller)
```

## 5. Phase 1 — one `Plugins` section

Low risk, no behavior change except 1.3.

**`components/Sidebar.tsx`**
- Replace `inventoryOpen` / `researchOpen` (182-184) with `pluginsOpen`.
- Replace the two section blocks (469-544) with one `Plugins` section, list id
  `sidebar-plugins`, `data-testid="plugins-nav"`.
- Rows in order: Visuals, Reports, Optimizers, Data.
- **Remove the `optimizersEnabled` gate** (192, 205-218, 502-512). The row
  renders unconditionally; the status effect moves out in phase 2.
- Rename the Data row label `Containers · Traces · Usage` → `Data`. Callback

- Keep `open-visuals`, `open-reports`, `open-optimizers`, `open-inventory`

- Give the four rows distinct glyphs. Today Visuals reuses `IconSearch` (the
  `Search` nav glyph) and Reports + Optimizers both use `IconInventory`; once
  they are adjacent in one section, three identical marks read as an error.
  Icons only — no explanatory prose in the sidebar.

**`App.tsx`** — no change required in phase 1. The four `*Active` props
(32-35) and four `onOpen*` callbacks (72-75) are already correct.

**Tests**
- `tests/playwright/optimizer-plugin-mcp.spec.ts:65` — invert and rename to

**Optional, low cost:** `runtime/evalApi.ts:85` exposes only `open-inventory`
(already named "Data") to the headless eval driver. Add the other three so a

## 6. Phase 2 — registry-driven status, one poller

**New `runtime/pluginPresentation.ts`** — the phase map hoisted from
`OptimizersPage.tsx:192-208`, plus `tone` / `isUsable` / `isTransitional` /
`a11yLabel`.

**New `runtime/pluginNav.ts`** — the static `PluginNavEntry[]` from §4.

**`hooks/useAppController.ts`**
- Own `pluginStatuses: PluginStatus[]` + `refreshPluginStatuses()` backed by
  `bridges.plugins?.list()`.
- Refresh on mount, on window focus, and on `optimizer:status` (§3.1) — add the
  `listen(EVENT_CHANNELS.OPTIMIZER_STATUS, …)` subscriber to `desktopBridge.ts`
  next to the Laguna one at 239.
- Bounded fallback poll **only while a status is transitional**
  (`downloading`, `verifying`, `starting`, `stopping`, `updating`, `removing`).

**`components/Sidebar.tsx`** — take `pluginStatuses` as a prop; per managed
entry, render `pluginPresentation(status).label` right-aligned and subdued, with
`a11yLabel` for non-normal states. Bridge absent (bombadil / browser runs):
render the row with **no** status text, never hidden.

**`components/OptimizersPage.tsx`** — take `plugin` + `onRefreshPlugin` as
props; delete `refreshPlugin` (134-138), the 750 ms interval (166-168), and the
local phase map; use `pluginPresentation`. Gate recipe-launch controls on
`isUsable` rather than rendering them unconditionally.

**`App.tsx`** — pass `pluginStatuses={c.pluginStatuses}` to `Sidebar`, and
status + refresh through `routes.tsx` to `OptimizersPage`.

**`src-tauri/src/lib.rs:995`** — validate `plugin_id` in `plugins_status`
instead of discarding it (§3.2); unknown id → `AppError`, matching
`plugins_set_release_channel:1011`. Regenerate the protocol; add a Rust test.

**Tests** — `ready` → `Ready`; `disabled` → visible + `Disabled` + opens;
`not_installed` → visible + `Not installed`; `error`/`degraded` → accessible
label, not color-only; bridge absent → nav usable, no status text, row present.

## 7. Phase 3 — lifecycle management (defer)

Do **not** start until phase 1+2 are landed, and re-scope per §1.2.

Required before any lifecycle button ships:

1. Plugin-level commands (`plugins_install/enable/disable/start/stop/update/remove/receipt`)
   composing `OptimizerSidecarManager` lifecycle + `registry.set_enabled` +
   `record_receipt`, behind `plugins/policy.rs` (`classify`, `auto_decision`,
   `plugin_kind`).
2. `service.activeRuns > 0` blocks or warns on destructive actions.
3. Every action returns a `PluginActionReceipt` with a fresh `PluginStatus`, and
   emits an event the controller already listens for.
4. Only then: a `PluginsPage` / detail panel, with `Recent activity` reading the
   64 retained receipts (`registry.rs:129-137`) rather than a new audit system.

A `Plugins` hub row (`All plugins`) is not worth building while `optimizers` is
the only managed plugin. The section header plus the Optimizers page is enough.

## 9. Amended acceptance criteria

1. Exactly one sidebar section, `Plugins`.
2. It provides **Visuals, Reports, Optimizers, Data** destinations (D1).
3. Routes, page state, and all four `open-*` test ids are unchanged.
4. Optimizers never disappears when disabled, stopped, uninstalled, or
   unhealthy — and `optimizer-plugin-mcp.spec.ts` asserts that, inverted.
5. Sidebar plugin state derives from `plugins.list()` via
   `pluginPresentation`, not a local boolean.
6. No lifecycle control is rendered for which a validated, policy-gated command
   does not exist.
7. Exactly one component polls or subscribes for plugin status, and the app no
   longer probes the sidecar every 750 ms from a mounted page.
8. The structure absorbs a second managed plugin as one more `PluginNavEntry`.

## 10. Risks

- **Concurrent worktrees.** Eight other workshop worktrees are checked out; two
  touch `Sidebar.tsx` lineage. Rebase `josh/v04` on `origin/dev` before landing
  and re-run the sidebar specs.
- **Test-id churn beyond the sidebar.** `evalApi.ts` and `UsageSheet.tsx` /
  `AccountPage.tsx` carry their own `*-open-inventory` ids. They are distinct
  strings and are not affected, but a blind rename sweep would break them.
- **`plugins_list` is single-element by construction.** Any UI that assumes the
  list enumerates all capabilities will render an empty Plugins section. The
  built-in entries must come from `pluginNav.ts`, never from the registry.
