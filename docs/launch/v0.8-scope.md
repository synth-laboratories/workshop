# v0.8 release scope

Status: implementation baseline
Date: 2026-08-24
Release thesis: **make the Synth frontend the place where a team can understand,
compare, reproduce, and promote model experiments, backed by cloud training,
Shoal-hosted Laguna, and explicit local Apple Silicon verification paths.**

This document consolidates the v0.8 plan across the web frontend and Workshop.
It promotes the experiment system and lineage/DAG viewer from the v0.7 deferred
list and makes them the organizing surface for two release programs:

1. hosted Laguna XS and Laguna S through Shoal; and
2. the NanoHorizon challenge, with a fast Modal iteration loop and a reproducible
   Mac MLX verification loop.

The release is not a collection of unrelated v0.7 deferrals. Work that does not
make one of these three outcomes substantially better is outside the v0.8 cut
line by default.

The executable repository lanes, frozen decisions, dependency order, and
integration gates are recorded in
[`v0.8-implementation-plan.md`](v0.8-implementation-plan.md). Changes to a P0
journey now require an explicit scope amendment rather than an informal backlog
edit.

## Release outcomes

v0.8 is complete when a user can perform these three journeys through their
declared product surfaces. Hosted Laguna ships through Workshop; NanoHorizon is
a web-frontend product beside Evals, with a separate Mac MLX verification
runner. NanoHorizon does not live in the Workshop app.

### 1. Understand an experiment

- Find an experiment by name, model, task, status, author, date, tag, or digest.
- Open a lineage graph that shows baselines, forks, reruns, training runs,
  checkpoints, evaluations, and promotions.
- Select any node to inspect its immutable inputs, state transitions, metrics,
  spend, artifacts, trajectories, and failure or promotion receipts.
- Compare related nodes without leaving the experiment workspace.
- Start a rerun or child experiment from a node without losing provenance.

The product reference is the interaction pattern in Eiso Kant's Model Factory
post: a searchable experiment index beside a navigable lineage canvas. The Synth
frontend must use its own visual language and its own typed run/candidate
contracts; the reference is an outcome and information-architecture target, not
a design to copy literally.

### 2. Use hosted Laguna in production

- Select hosted Laguna XS or Laguna S as an explicit Shoal target.
- See availability, expected price, quota, and any degraded state before launch.
- Run a real Responses/tool workflow with durable usage and routing receipts.
- Survive retryable failures without duplicate billing or duplicate work.
- Reconcile after Workshop, broker, or worker restart.
- Inspect the exact model/candidate revision, serving revision, cost, and request
  lineage in the experiment view.
- Canary and roll back a Laguna candidate using immutable promotion receipts.

Both models are v0.8 release requirements. A catalog entry or a successful
one-off request is not shipment.

### 3. Complete the NanoHorizon loop

- Open a versioned NanoHorizon challenge with a pinned task, starter policy,
  baseline, metric, budget, and submission contract.
- Edit and run a small iteration on Modal quickly, without rebuilding unrelated
  infrastructure.
- See every iteration, score, artifact, and parent/child relationship in the
  experiment view.
- Select a candidate and reproduce or evaluate it on Mac with MLX against the
  same declared task contract and seed ledger.
- Compare Modal and MLX results honestly, with backend and numerical differences
  recorded rather than hidden.
- Export a submission/evidence bundle another developer can rerun from the
  published instructions.

## P0 release pillars

### A. Experiment API, store, and lineage viewer

The experiment system is a product surface backed by durable contracts, not a
UI-only graph over ad hoc job records.

#### Canonical objects

| Object | Required identity |
| --- | --- |
| Experiment | `experiment_id`, owner/project, title, tags, created time |
| Run | `run_id`, `experiment_id`, recipe/config digest, task contract, backend, state |
| Candidate | `candidate_id`, content digest, kind, parent candidates, producing run |
| Artifact/checkpoint | artifact digest, base-model digest, format, producing run |
| Evaluation | evaluator/task digest, candidate digest, seed ledger, result digest |
| Trajectory bundle | immutable trace references and digests, policy and task identity |
| Promotion | source candidate, target, approval, canary, rollback candidate, receipt |

#### Canonical edges

- `forked_from`
- `rerun_of`
- `warm_started_from`
- `produced`
- `evaluated`
- `compared_with`
- `promoted_to`
- `reproduced_on`
- `rolled_back_to`

Edges are typed, append-only facts. The viewer must not infer lineage from names
or timestamps when an authoritative edge can be recorded.

#### Required UI

- Searchable/filterable experiment list with status and recent-result summaries.
- Pan/zoom lineage canvas with automatic layout and a usable compact-window mode.
- Node detail drawer for configuration, metrics, cost, artifacts, trajectories,
  logs, and receipts.
- Side-by-side comparison for two or more compatible nodes.
- Clear visual distinction between queued, active, completed, failed, cancelled,
  degraded, promoted, and rolled-back states.
- Actions for rerun, fork, compare, open artifact, open trajectories, and promote,
  shown only when admitted by the underlying contract.
- Durable view state and deep links.

#### API and storage requirements

- Versioned create/list/get/search APIs for experiments, nodes, and edges.
- Idempotent event ingestion and cursor-based subscriptions.
- One authoritative experiment projection that can be rebuilt from durable run,
  candidate, evaluation, artifact, and promotion facts.
- Immutable trajectory/evidence references; large trace bodies stay in the
  artifact store rather than the graph database.
- Access control and redaction applied before indexing or rendering.
- Migration path for useful v0.7 runs without inventing missing provenance.

### B. Shoal-hosted Laguna XS and Laguna S

Shoal needs an explicit production contract across control state, request logic,
capacity, accounting, and promotion.

#### Service state machine

The serving-target lifecycle uses a single durable state model:

```text
registered -> validating -> queued -> provisioning -> warming -> ready
                                              |          |        |
                                              v          v        v
                                            failed     failed   degraded
                                                                  |
ready/degraded -> draining -> stopped <---------------------------+
       |
       +-> rolling_back -> ready(previous candidate) | failed
```

Every transition records actor, reason, prior and next state, candidate digest,
serving revision, time, and an idempotency key. Observed worker health never
silently overwrites desired state. Reconciliation converges the two and emits a
receipt when it cannot.

Request execution separately records `admitted -> reserved -> routed -> active ->
completed|failed|cancelled`. Retries preserve one logical request and distinguish
unbilled pre-execution failures from billable inference.

#### Routing and correctness

- Laguna XS and S have distinct immutable target identifiers and capability
  declarations; no floating `latest` route is used for release evidence.
- Responses is the production distribution for Codex; native Chat Completions
  remains a separately tested contract where required.
- Admission checks model availability, context/tool compatibility, account plan,
  quota, spend controls, and regional/capacity policy before reservation.
- A request pins one model candidate and serving revision for its lifetime.
- Retries, cancellation, streaming disconnects, and worker loss have documented
  ownership and idempotency behavior.
- Promotion requires offline, tool-use, safety, serving-compatibility, canary, and
  rollback receipts tied to the exact artifact digest.

#### Production economics

v0.8 must ship an inspectable economic ledger, not merely a token counter.

For each target and request, record:

- input, cached-input, reasoning, and output tokens where the model exposes them;
- GPU class, reserved/active/idle seconds, batch occupancy, and serving revision;
- provider/infrastructure cost, attributed cost, user charge, credit adjustment,
  and currency;
- reservation, authorization, settlement, refund/credit, and reconciliation IDs;
- warm-pool and failed-capacity cost separately from billable inference;
- the pricing/tariff version used for the estimate and final settlement.

The release must choose and document:

- the unit shown to users and how estimates become final charges;
- XS versus S prices and any plan-included allowance;
- rate limits, concurrency limits, monthly quota, and overage behavior;
- who pays for cold starts, retries, provider faults, abandoned streams, and
  canary capacity;
- margin and capacity guardrails, including the action taken when breached.

Numbers remain an explicit product/finance decision. Engineering may implement
the versioned ledger and simulator before final tariffs are selected, but v0.8
cannot ship hosted Laguna with placeholder or ambiguous billing semantics.

#### Shoal acceptance gates

- Packaged Workshop E2E for XS and S through the production-equivalent Shoal path.
- Responses streaming and tool loop, cancellation, retry, timeout, and restart.
- No duplicate charge or duplicate generation under injected retry races.
- Capacity loss transitions to degraded/draining and recovers by reconciliation.
- Usage dashboard totals reconcile to request receipts and infrastructure ledger
  within a declared tolerance.
- Canary promotion and forced rollback for both models.
- Load, latency, saturation, and cost tests at declared launch concurrency.
- Security review: credentials use only already-authorized non-Keychain paths;
  no provider secret or raw credential enters a trajectory or experiment index.

### C. NanoHorizon challenge: Modal to Mac MLX

NanoHorizon is the v0.8 reference workflow proving that the experiment system is
useful for real iteration rather than only retrospective visualization.

The detailed product and implementation scope is in
[`v0.8-nanohorizon-frontend.md`](v0.8-nanohorizon-frontend.md).

#### Challenge package

- Versioned challenge statement and scoring rules.
- Pinned Craftax task/container contract, seed ledger, baseline, and resource
  budget.
- Small starter policy and one known-good smoke submission.
- Separate visible development and held-out evaluation sets.
- Submission schema with source, config, dependency, artifact, trajectory,
  metric, and cost digests.
- Clear rules for what may change: policy/prompt, SFT data, adapter/training
  configuration, and any later admitted lever.

#### Fast Modal loop

The documented happy path should be short:

1. fork the starter experiment;
2. edit a policy or training recipe;
3. run a bounded smoke;
4. inspect trajectories and metrics;
5. fork or rerun from the selected node;
6. launch the larger Modal evaluation only after the smoke passes;
7. retain the exact candidate and result bundle.

Modal is the fast cloud iteration backend, not a source of truth for identity.
Task, candidate, artifact, configuration, and seed digests remain portable.

#### Mac MLX verification

- Import or convert the selected candidate into a declared MLX-compatible
  artifact; never substitute an ambient checkpoint.
- Verify base-model, tokenizer, adapter, quantization, renderer, task, and seed
  identities before evaluation.
- Run a bounded local smoke and the published paired evaluation.
- Attach a `reproduced_on` edge from the Modal candidate to the MLX result.
- Report score, latency, memory, generation settings, and any numerical/backend
  divergence. “Reproduced” means declared equivalent inputs and an explicit
  tolerance, not bit identity across CUDA and MLX.
- Make the local path reproducible through a standalone CLI runner and return
  its receipt to the frontend. It is not a Workshop app workflow.

#### NanoHorizon acceptance gates

- A browser-only user can fork, preflight, and run a Modal smoke without
  installing Workshop or local MLX.
- A supported Mac can complete standalone CLI setup and MLX verification without
  Workshop.
- The page's generated coding-agent prompt can install or verify Workshop plus
  the pinned NanoHorizon toolchain, reach preflight, and stop before paid compute.
- A clean-machine developer can follow the published Modal instructions.
- The smallest edit-to-result loop meets a declared target time and spend budget.
- At least three related iterations render correctly as a lineage graph.
- One Modal-trained candidate completes the Mac MLX verification path.
- The same held-out seeds are used for the declared paired comparison.
- Exported evidence is sufficient for another developer to rerun without local
  absolute paths or undeclared state.
- Challenge submission and leaderboard integration use a stable API and preserve
  candidate/git evidence.

## Shared foundation

The three pillars depend on the portable-candidate work already designed for
v0.8:

- `synth.candidate.v1` and `synth.task-contract.v1`;
- content-addressed candidates and task contracts;
- register-then-run container execution;
- explicit `rerun_of`, attempt, and substitution lineage;
- immutable artifact and trajectory references;
- parity-tested canonicalization across Rust and Python;
- a frontend rerun action backed by a typed request, not reconstructed prose.

This is the common identity layer for the DAG, Shoal promotion, and Modal-to-MLX
reproduction. It should land before each product surface invents a local schema.

## Milestones and dependency order

Milestones are exit criteria, not calendar promises.

### M0 — Freeze contracts and economics decisions

- Approve v0.8 scope and non-goals.
- Freeze experiment node/edge schemas and the portable candidate/task contracts.
- Freeze Shoal desired/observed state semantics and request idempotency model.
- Select launch tariff policy, quota behavior, and failure/refund rules.
- Freeze the NanoHorizon challenge and cross-backend equivalence contract.

### M1 — Durable experiment spine

- Versioned experiment APIs and projection store.
- Event ingestion from Eval, GEPA, training, MLX, Shoal, and promotion paths.
- Search, experiment list, node detail, and basic lineage graph on fixture and
  migrated real runs.

### M2 — NanoHorizon vertical slice

- Starter challenge and bounded Modal workflow.
- Candidate/result ingestion into the experiment system.
- Mac MLX import and paired verification.
- One complete Modal -> DAG -> MLX evidence bundle.

### M3 — Shoal production candidate

- XS and S lifecycle controller, reconciler, routing, and immutable revision pins.
- Economic ledger, estimates, settlement, credits, quotas, and usage projection.
- Canary/rollback and failure-injection receipts.
- Both models visible in the same experiment/promotion graph.

### M4 — Product-quality experiment workspace

- Compare, filters, durable view state, trajectory links, costs, promotion
  controls, accessibility, and compact-window behavior.
- Scale and performance tests on realistic experiment counts and graph depth.

### M5 — Release qualification

- Packaged clean-install E2Es for the three release journeys.
- Production-equivalent Shoal load/economics/security review.
- NanoHorizon instructions reproduced by a second clean environment.
- Signed provenance, rollback package, release notes, and support runbook.

## P1 extensions after the vertical slices

These belong in v0.8 only after the P0 journeys are healthy:

- process/milestone rewards and their one-term-at-a-time ablations;
- annotation and trajectory analysis in the experiment detail view;
- richer chart interactions and linked graph/table selection;
- public cookbook download UX when it produces a runnable experiment;
- checkpoint tags and library polish that support candidate selection;
- hosted OHCO/GELO only with independent mechanism and economics acceptance;
- consent-safe analytics needed to understand funnel and reliability.

## Explicit non-goals

- A generic free-form whiteboard or manually authored DAG.
- A graph that infers authoritative lineage from display names.
- Shipping every item deferred from v0.7.
- Claiming CUDA/MLX bit-exactness for sampled generation.
- Automatic production promotion without an explicit approval and rollback target.
- Storing provider credentials, secrets, or raw secret-bearing requests in the
  experiment/trajectory store.
- Keychain-backed provider credentials for code or release workflows.
- Mixing held-out NanoHorizon evidence into training or candidate selection.

## Release scorecard

The final go/no-go report must answer, with retained receipts:

| Question | Required answer |
| --- | --- |
| Can users find and understand related experiments? | Yes, on real multi-run data |
| Is every rendered edge backed by durable lineage? | Yes |
| Can a result be rerun or forked without provenance loss? | Yes |
| Are Laguna XS and S both production-ready through Shoal? | Yes |
| Are desired/observed state and request retries proven under faults? | Yes |
| Do charges reconcile to versioned tariffs and infrastructure usage? | Yes |
| Can a developer iterate on NanoHorizon quickly with Modal? | Yes |
| Can the selected result be evaluated on Mac MLX? | Yes |
| Are backend differences and tolerances explicit? | Yes |
| Is rollback proven for models, services, and the desktop release? | Yes |

Any “no” keeps the corresponding pillar out of the release claim; Laguna XS and
S, the experiment/DAG workspace, and the NanoHorizon Modal-to-MLX journey are all
declared P0, so omission of any one requires a deliberate v0.8 scope revision.

## Launch values still to measure

The product architecture and release cut are frozen in the implementation plan.
The following values must be filled from measured evidence before their
corresponding production gates open; they are configuration inputs, not open
scope questions:

1. approved Laguna XS and S tariff rates, plan allowances, quotas, and overage
   values;
2. measured CUDA/SGLang-to-MLX equivalence tolerances by NanoHorizon metric;
3. launch concurrency, regions, warm-pool sizes, and SLO thresholds for each
   Laguna target; and
4. named human owners, reviewers, and calendar dates for each gate.
